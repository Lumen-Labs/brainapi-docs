# Public shared brain revenue share

A publisher can enable revenue share on a public listing, connect a Stripe account, and see earnings and transfers. Visitors use the existing browser flow or copy a revocable token for an app or MCP. The visitor's authorized billing team funds the query. A publisher earns a percentage of the verified paid-credit value consumed by an eligible query.

## Proposed contracts

- **Eligibility.** Accrue only for a live, monetized public listing queried by an authorized visitor whose paying team differs from the publishing team. An approved policy version supplies the rate in basis points and the eligible operation price or rate card. Snapshot listing ID, publisher, payee, payer, currency and policy when a query is admitted. Preserve accrued earnings and historical payee attribution when the listing is unpublished, made team-only or transferred. A query admitted before a change can settle under its snapshot if it reaches the billable success boundary.
- **Credit value.** Start with provably purchased dollar-credit packs, preserve existing allowance precedence, and require existing billing authorization for paid fallback. Existing aggregate balances remain spendable under existing rules. Only reconciled purchase amounts qualify for revenue share. Query top-up credits and subscription allowances need an explicit valuation policy before they qualify. Use fixed-point money and carry fractional minor units forward by payee and currency.
- **One settlement per billable operation.** Use the current billable retrieval unit, subject to contract verification across browser and gateway paths. A successful retrieval can count even if answer generation later fails, provided the existing query contract bills that retrieval. Reserve funds before execution, release failed or canceled work before the success boundary, and settle debit, funding allocations, earnings and invoice-exclusion evidence atomically. Durable operation IDs, request fingerprints and payer-scoped idempotency prevent duplicate spend or conflicting replays. Commit settlement before exposing retrieval results or passing them into the browser answer stream. Included queries retain usage records and yield zero earnings. Keep Explore and metadata, authentication and MCP discovery outside paid execution.
- **One public query boundary.** Browser requests keep session authentication. App clients use a Bearer credential on a public-listing query route. MCP exposes only the same query operation through a listing-specific Streamable HTTP adapter. Bind credentials to the viewer, listing ID and authorized payer team. Store only the digest and safe metadata, show the secret once, and recheck membership, listing state, visitor permissions and limits on each paid call. Rotate or revoke without changing the publishing brain's key. Invalidate old keys on changes that remove public access. Authenticate internal attribution and strip client-supplied payer and listing overrides. Fail closed if the shared payer cannot be resolved at either the application or Go proxy boundary. Keep the existing deployment API and MCP paths available under their current credentials.
- **Stripe.** Keep customer credit purchases on the platform. Use hosted Connect onboarding for the approved publisher payee and separate transfers from available platform funds for accrued earnings. Record a platform transfer separately from a Stripe bank payout. Stripe return redirects trigger a status refresh. Readiness comes from Stripe account state and verified events. Confirm the account configuration, corridors and currency support in test mode before enabling real settlement. [Hosted onboarding](https://docs.stripe.com/connect/hosted-onboarding), [Separate charges and transfers](https://docs.stripe.com/connect/separate-charges-and-transfers)
- **Adjustments.** Link each allocation to a funding payment so partial refunds and disputes can append compensating entries. Hold or offset earnings when funds are disputed. After transfer, use a tracked reversal where available and a recoverable balance when a reversal fails. Dedupe webhook deliveries and domain transitions. Reconcile unknown Stripe transfer outcomes before retrying beyond the provider's idempotency window. [Transfer reversals](https://docs.stripe.com/api/transfer_reversals), [Stripe idempotency](https://docs.stripe.com/api/idempotent_requests)

## Checkpoints and rollout

1. **After 1–3** run the existing wallet, billing-cycle and Stripe webhook suites and replica-set tests. Reconcile aggregate wallet balances against funding allocations and legacy residuals before enabling paid query spending.
2. **After 4–6** run Hub access and Ask tests, billing aggregation and focused settlement concurrency tests. In staging, reconcile a single browser retrieval across payer balance, usage and publisher earnings. Check that paid settlement failures prevent delivery under the paid contract.
3. **After 7–9** prove browser, app and MCP attribution matches for the same listing. Test real MCP clients with Bearer support and confirm Stripe setup with test credentials. Run Next.js `npm test` and `npm run typecheck:ci`, plus Go `go test ./...` for any metering change and targeted pytest if the adapter changes brainapi2.
4. **After 10–12** replay Stripe fixtures and verify balances against transfers and reversals in test mode. Document the REST contract and token copy/setup steps in the docs repo. Canary independently with credential access, accrual and transfers gated. Start with test mode, then enable a limited publisher cohort after policy approval and reconciliation. An incident can pause new accrual and outbound transfers independently while retaining ledger and pending reconciliation.

## Decisions for review

| Decision | Proposed starting point |
| --- | --- |
| Revenue share rate and eligible price | One platform-managed rate with effective dates. Confirm the percentage, the retrieval rate and the exact success boundary. Existing billable retrieval units give browser/API/MCP a shared unit. |
| What counts as purchased credits | Verified dollar packs first. Decide whether paid query packs enter launch scope and whether to allocate a portion of paid subscription invoices to their query allowances. Those paths need actual paid amount, grant lineage, expiry and refund rules. |
| Gross or net basis | Actual credit funding after discounts and before processor fees, excluding taxes and adjusted for refunds. Validate economics and define treatment of credits purchased at legacy prices. |
| Buyer spending policy | Included allowance first. Paid fallback uses existing team billing authorization and explicit payer binding on issuance. Confirm which roles can issue a team-funded credential and whether payer caps are required at launch. |
| Publisher payee | Publishing team as payee, with the team owner managing Stripe. Confirm eligibility for personal teams, transfer of ownership, and treatment of outstanding balances on deactivation. |
| Settlement policy | Select supported launch currencies and countries, hold period, cadence, minimum transfer and treatment of negative balances before real transfers. |
| MCP compatibility | Bearer-capable clients in the first slice. Add a narrow OAuth exchange only if required by named clients, using the same listing and payer scope. |

Tasks 5 and 9 can proceed alongside wallet and query work after task 1 locks the contracts. Start the consumer UI against the agreed credential DTO while the gateway is implemented. Sequence wallet writers and settlement migrations, and keep Stripe transfer execution behind the adjustment and reconciliation checkpoint.
