---
title: BrainAPI Authentication and Brains
description: Authenticate requests and keep every BrainAPI operation in the intended brain
---

Protected core requests need a valid PAT. Most data requests also need a brain identifier. Treat the token as authorization and the brain as the data boundary; do not infer either from user-provided content.

`X-Brain-ID` is the alphanumeric Brain ID from the dashboard Settings page (`name_key`), not the display name. Letters and digits only: `supportkb` is valid, `Support KB` and `support-kb` are not.

## Token types

| Token | Scope | Use it for |
| --- | --- | --- |
| System `BRAINPAT_TOKEN` | All brains and `/system/*` | Administration, brain creation, trusted operations. |
| Brain PAT | One stored brain | Application requests limited to that brain. |

Send either header form:

```http
BrainPAT: <token>
```

```http
Authorization: Bearer <token>
```

Examples in these docs use `BrainPAT` because it avoids ambiguity with other bearer-token middleware.

## Select a brain

BrainAPI resolves a brain in this order:

1. `X-Brain-ID` header.
2. `brain_id` query parameter.
3. Top-level `brain_id` in a JSON body for `POST`, `PUT`, or `PATCH`.
4. `brain_id` multipart field for file uploads.

Use `X-Brain-ID` in new integrations so routing is consistent across methods and body formats.

```bash
curl http://localhost:8000/meta/entity-labels \
  -H "BrainPAT: $BRAINPAT_TOKEN" \
  -H "X-Brain-ID: supportkb"
```

Brain IDs must be alphanumeric (`str.isalnum()`) in ordinary data requests. The reserved `system` brain cannot be used as application data. Creating a brain through `POST /system/brains` also requires the ID to start with a letter.

## Create or resolve brains

`BRAIN_CREATION_ALLOWED=true` lets middleware create a missing named brain when a valid request selects it. `DEFAULT_BRAIN_FALLBACK=true` selects or creates `default` when no brain is supplied. For explicit administration, use the system token:

```bash
curl --fail-with-body -X POST http://localhost:8000/system/brains \
  -H "BrainPAT: $BRAINPAT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"brain_id":"supportkb"}'
```

For production, prefer explicit brain creation and pass the intended brain on every request. Automatic creation is convenient during development but can hide spelling mistakes.

## Resolve a token

`GET /meta/login-info` is exempt from brain selection and tells a console or client whether a PAT is the system token or belongs to one brain.

```bash
curl http://localhost:8000/meta/login-info \
  -H "BrainPAT: $BRAINPAT_TOKEN"
```

## Token scopes

Default PAT scopes are `brainapi`. Expert verification writes (`POST /model/facts/{id}/verify|reject|reset` and conflict `method=verified_side`) also need `verification`. That scope is **not** granted by default. Self-host Compose templates set `BRAINPAT_SCOPES="brainapi verification"` so the system PAT can verify facts. `POST /system/brains` accepts optional `pat_scopes` (`brainapi` and/or `verification`). Existing brains with empty `pat_scopes` stay `brainapi`-only.

- System PAT: space-separated `BRAINPAT_SCOPES`.
- Brain PAT: stored `pat_scopes` on that brain.

`GET /system/brains-list` requires the system PAT. Brain keys are omitted unless you pass `?include_pats=true`.

Resolved scopes are cached for 30 seconds. See [Fact verification](/v2/retrieval/verification).

v2.21.0 has no `POST /system/brains/{brain_id}/rotate-pat`. The engine issues a brain PAT when the brain is created. Do not call rotate-pat against this version.

## Clear or delete a brain

Use the system PAT for these destructive operations. Stop active imports and take a backup first if you need to retain the data.

| Request | Effect |
| --- | --- |
| `POST /system/brains/{brain_id}/clear` | Removes the brain's data and keeps its ID and PAT. |
| `DELETE /system/brains/{brain_id}` | Removes the data, registered brain identity, PAT, and cached credentials. |

A **409** means another lifecycle operation is running. A **503** with `BRAIN_CLEANUP_FAILED` lists the failed backends. Check their health, then retry the same operation. Clearing an unknown brain returns **404**.

## Failure behavior

| Status | Meaning | Check |
| --- | --- | --- |
| `400` `BRAIN_ID_INVALID` | The supplied ID is not alphanumeric (hyphens, spaces, punctuation). | Use the dashboard Brain ID, letters and digits only. |
| `400` `BRAIN_ID_RESERVED` | The reserved `system` brain was selected. | Choose an application brain. |
| `401` | PAT is missing, malformed, or does not match the brain. A missing PAT is `401`, not `400`. | Token source and selected brain. |
| `403` `VERIFICATION_PERMISSION_DENIED` | The PAT lacks the `verification` scope. | Grant the scope; wait up to 30 seconds for cache expiry. |
| `406` | No brain resolved, or the named brain does not exist and automatic creation/fallback is off. Omitting `X-Brain-ID` with fallback off is `406`, not `400`. | Send a valid Brain ID or create the brain with the system PAT. |
| `503` | Brain lookup could not reach the data store. | Connection and credentials. |

## Security guidance

- Keep the system token in trusted operator services; give applications brain-scoped PATs.
- Never put PATs in URLs, examples committed to source, browser logs, or analytics.
- Validate the caller's tenant-to-brain mapping before forwarding `X-Brain-ID`.
- Rotate a leaked PAT and clear any intermediary cache that stored it.

See [Errors and HTTP statuses](/v2/reference/errors) for cross-API behavior.
